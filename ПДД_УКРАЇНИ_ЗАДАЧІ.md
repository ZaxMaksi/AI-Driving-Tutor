# Задача: Подготовка базы данных ПДД Украины и системы хранения вопросов с изображениями

## 1. Контекст проекта

Ты работаешь над проектом **AI Driving Tutor** — образовательным веб-приложением для изучения Правил дорожного движения Украины и подготовки к теоретическому экзамену.

Текущий стек проекта:

### Backend
- Python 3.12.10
- Django 5.2
- Django REST Framework
- PostgreSQL 18
- psycopg
- Pillow
- django-environ

### Frontend
- React
- TypeScript
- Vite

### AI
- Google Gemini API
- SDK: google-genai

Архитектура проекта — модульный монолит на Django.

Основные приложения Django:
- `users` — пользователи и авторизация.
- `traffic_rules` — нормативные материалы ПДД.
- `questions` — вопросы, варианты ответов и изображения.
- `testing` — прохождение тестов и проверка ответов.
- `progress` — статистика и прогресс.
- `ai_tutor` — интеграция Gemini.

## 3. Источник нормативных материалов

Основной источник:

Официальный портал Верховной Рады Украины:

https://zakon.rada.gov.ua/laws/show/1306-2001-%D0%BF#Text

Документ: Постановление Кабинета Министров Украины № 1306 от 10.10.2001 «Про Правила дорожнього руху».

Требования:

- Использовать официальный источник как основной.
- Проверить актуальную редакцию документа.
- По возможности определить дату последнего изменения.
- Сохранить ссылку на официальный документ.
- Не использовать сторонние сайты как источник нормативной истины.
- Не выдавать устаревшие редакции за актуальные.
- Если невозможно проверить актуальную редакцию, явно указать это в отчёте.

Если официальный источник предоставляет доступный формат для автоматизированного получения текста, исследуй его возможности.

Не придумывай API, если не удалось подтвердить его существование.

Если автоматическое получение документа невозможно, подготовь понятный механизм ручного импорта и укажи, какие действия должен выполнить разработчик.

## 4. Структурирование ПДД в Markdown

Подготовь каталог:

`backend/data/traffic_rules/`

В нём должны находиться:

- `traffic_rules.md` — полный структурированный текст ПДД.
- `metadata.json` — информация об источнике и редакции документа.
- При необходимости — отдельные Markdown-файлы для крупных разделов.

Структура Markdown должна сохранять оригинальную нумерацию и иерархию документа.

Пример:

# Правила дорожного руху України

## Розділ 1. Загальні положення

### Пункт 1.1

Оригинальный текст нормативного документа.

### Пункт 1.2

Оригинальный текст нормативного документа.

## Розділ 2. Обов'язки і права водіїв

### Пункт 2.1

Оригинальный текст нормативного документа.

Требования:

- Не изменять юридический смысл оригинального текста.
- Не сокращать нормативные положения.
- Сохранять номера разделов, пунктов и подпунктов.
- Сохранять определения терминов.
- Не смешивать собственные пояснения с нормативным текстом.
- Не генерировать отсутствующие пункты.

Если текст невозможно получить полностью, не создавай фиктивный полный документ.

### metadata.json

Предусмотреть следующие поля:

- название документа;
- номер постановления;
- дата принятия;
- дата редакции;
- дата получения документа;
- официальный URL;
- статус проверки актуальности;
- контрольная сумма исходного документа, если возможно.

## 5. Архитектура PostgreSQL

Изучи существующие модели проекта и подготовь модели Django для приложения `traffic_rules`.

Предусмотри хранение:

### Нормативного документа

Например:
- название;
- номер документа;
- источник;
- дата редакции;
- дата импорта;
- статус актуальности;
- версия документа.

### Разделов ПДД

Например:
- название раздела;
- номер раздела;
- описание;
- связь с нормативным документом.

### Пунктов ПДД

Например:
- номер пункта (`1.1`, `1.2`, `2.3` и т. д.);
- оригинальный текст;
- связь с разделом;
- порядок отображения;
- ссылка на источник, если доступна.

Продумай возможность изменения нормативных материалов в будущем.

Важно: при обновлении ПДД не следует бесконтрольно перезаписывать старые данные. Необходимо сохранять информацию о версиях и иметь возможность определить, к какой редакции относится конкретный пункт.

Не создавай избыточно сложную систему версионирования. Она должна соответствовать масштабу учебного проекта.

## 6. Архитектура вопросов с изображениями

Работай в Django-приложении `questions`.

Изучи уже существующие модели. Если их нет, подготовь необходимые.

Вопрос должен поддерживать:

- текст вопроса;
- несколько вариантов ответа;
- правильный вариант ответа;
- объяснение правильного ответа;
- связь с темой или категорией;
- связь с пунктами ПДД;
- одно или несколько изображений;
- тип вопроса: официальный или сгенерированный ИИ;
- статус проверки ИИ-вопроса.

### Изображения

Используй Django `ImageField` и Pillow.

Для начала используй локальное хранилище Django Media Storage.

Рекомендуемая структура:

`backend/media/questions/`

Изображения должны быть физическими файлами, а PostgreSQL должен хранить только ссылки и метаданные.

Предусмотри возможность:

- одного изображения;
- нескольких изображений;
- сортировки изображений;
- необязательного описания изображения;
- определения основного изображения.

Не сохраняй изображения непосредственно в PostgreSQL в виде BLOB или Base64.

Не добавляй изображения в Git.

### Типы вопросов

Разделяй:

1. Официальные вопросы.
2. Сгенерированные Gemini вопросы.

Для сгенерированных вопросов предусмотрены статусы:

- `pending` — ожидает проверки;
- `approved` — проверен и одобрен;
- `rejected` — отклонён.

ИИ-вопросы не должны автоматически становиться официальными.

### Проверка ответов

Правильный ответ должен определяться исключительно backend на основании данных PostgreSQL.

Gemini не должен самостоятельно определять результат экзамена или начислять баллы.

## 7. Подготовка данных для Gemini

Предусмотри возможность последующего использования нормативных материалов в `ai_tutor`.

Не нужно сейчас реализовывать полноценную RAG-систему.

Но архитектура должна позволять:

1. Получить вопрос пользователя.
2. Определить связанные с ним темы или пункты ПДД.
3. Извлечь соответствующие нормативные положения из PostgreSQL.
4. Передать их Gemini в качестве контекста.
5. Получить объяснение с опорой на переданные материалы.

Для каждого нормативного фрагмента должна сохраняться идентификация:

- номер пункта;
- раздел;
- редакция документа;
- источник.

Gemini не должен представлять собственные предположения как нормативный факт.

- определение разделов и пунктов;

- проверка корректности структуры;

- понятный отчёт об импорте.

Если документ изменился, не перезаписывай старую редакцию без сохранения истории.
