# 1. Описание проекта

## 1.1. Название

**AI Driving Tutor**

## 1.2. Идея проекта

AI Driving Tutor — веб-приложение с интеграцией большой языковой модели (LLM), предназначенное для изучения Правил дорожного движения Украины и подготовки пользователей к теоретическому экзамену на получение водительского удостоверения.

Основная идея заключается в объединении традиционной системы тестирования с возможностями искусственного интеллекта.

Пользователь сможет проходить тесты, изучать отдельные темы ПДД, анализировать собственные ошибки и получать персонализированные объяснения от ИИ.

В отличие от обычных тестовых приложений, AI Driving Tutor будет использовать Gemini API для генерации дополнительных учебных вопросов, объяснения сложных ситуаций и адаптации учебного процесса к знаниям пользователя.

## 1.3. Цель проекта

Разработать полноценное веб-приложение, демонстрирующее практическое применение LLM в реальном программном продукте.

Проект должен продемонстрировать:

- Разработку backend на Django и Django REST Framework.
- Проектирование реляционной базы данных PostgreSQL.
- Создание REST API.
- Интеграцию внешней LLM через Gemini API.
- Использование ИИ для генерации структурированных данных.
- Использование контекста и исходных нормативных материалов для повышения достоверности ответов модели.
- Разработку frontend на React и TypeScript.
- Реализацию аутентификации, тестирования и сохранения пользовательского прогресса.

Главный акцент проекта — не просто использование API языковой модели, а правильная архитектурная интеграция ИИ в приложение.

- Переходить к тестам по выбранным темам.

## 4.3. Тестирование

Предусмотреть несколько режимов:

- Тестирование по отдельной теме.
- Тестирование по нескольким выбранным темам.
- Смешанный тест.
- Полноценный экзаменационный режим.
- Дополнительные тренировочные вопросы, созданные ИИ.

Возможности:

- Отображение вопроса и вариантов ответа.
- Поддержка изображений.

- Переход между вопросами.
- Отображение результатов.
- Сохранение истории прохождения.

## 4.4. Работа с ошибками

После прохождения теста пользователь должен видеть:

- Свои ответы.

- Объяснение правильного ответа.
- Ссылку на соответствующую тему ПДД.

Дополнительно Gemini должен уметь объяснять, почему выбранный пользователем вариант неправильный.

- Количество пройденных тестов.
- Общий процент правильных ответов.
- Количество ошибок.

- Темы, в которых пользователь чаще всего ошибается.
- Динамику результатов.
- Рекомендации по повторению слабых тем.

Главная интеллектуальная составляющая приложения.

# 6. Важнейший архитектурный принцип: контроль достоверности ИИ

Это одно из главных требований проекта.

**Gemini не должен самостоятельно определять результат тестирования.**

Правильность ответа всегда проверяет backend на основании данных, сохранённых в PostgreSQL.

Пример:

1. Backend получает вопрос из базы.
2. Пользователь выбирает ответ.
3. Backend сравнивает выбранный вариант с правильным ответом в базе.
4. Backend самостоятельно рассчитывает результат.
5. При необходимости backend отправляет информацию в Gemini для объяснения ошибки.
6. Gemini возвращает текстовое объяснение.
7. Backend проверяет ответ модели и передаёт его frontend.

Таким образом, LLM отвечает за интеллектуальную составляющую, но не за критически важную бизнес-логику.

## 6.1. Защита от галлюцинаций

Для генерации вопросов необходимо:

- Передавать модели конкретные нормативные материалы.
- Использовать структурированный формат ответа.
- Проверять JSON и обязательные поля.
- Проверять количество вариантов ответов.
- Проверять корректность идентификатора правильного ответа.
- Сохранять источник, на основании которого создан вопрос.
- Не допускать автоматического попадания непроверенных вопросов в основную базу экзаменационных вопросов.

Вопросы, созданные ИИ, должны иметь отдельный статус, например:

- `pending` — ожидает проверки.
- `approved` — проверен и допущен к использованию.
- `rejected` — отклонён.

На первом этапе допустимо использовать сгенерированные вопросы только в тренировочном режиме.

## 6.2. Надёжность интеграции

Предусмотреть:

- Обработку ошибок Gemini API.
- Обработку превышения лимитов запросов.
- Таймауты.
- Повторные запросы только там, где это безопасно.
- Проверку пустых и некорректных ответов.
- Логирование ошибок без сохранения секретных данных.
- Возможность ограничивать количество запросов на пользователя.

# 8. Дополнительные технические требования

## 8.1. Безопасность

- Не хранить API-ключи в исходном коде.
- Использовать `.env` для секретных настроек.
- Не передавать секреты frontend.
- Использовать Django permissions.
- Проверять принадлежность пользовательских данных.
- Ограничивать доступ к персональной статистике.
- Валидировать все входные данные.
- Не доверять данным, полученным от LLM.

## 8.2. Качество кода

- Использовать понятную структуру проекта.
- Соблюдать принципы DRY и SOLID там, где они уместны.
- Не создавать чрезмерно сложную архитектуру.
- Разделять бизнес-логику, представления и интеграции.
- Использовать type hints в Python.
- Писать понятные имена переменных и функций.
- Не дублировать логику между приложениями.
- Документировать сложные участки кода.

## 8.3. Логирование

Предусмотреть логирование:

- Ошибок backend.
- Ошибок базы данных.
- Ошибок Gemini API.
- Неудачных операций генерации.
- Некорректных ответов модели.

Не записывать пароли, токены и API-ключи в логи.

## 8.4. Тестируемость

Каждый важный сервис должен быть спроектирован так, чтобы его можно было тестировать независимо.

Для тестов Gemini использовать mock-ответы, чтобы не расходовать API-квоту при каждом запуске тестов.
